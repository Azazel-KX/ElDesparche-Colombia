ALCANCE Y CAMBIOS EN LA VERSIÓN 1.4 (correcciones técnicas tras revisión de diseño)
----------------------------------------------------------------------------------------------------------------------------------
  - TOTALIDAD DE LA HERENCIA: ADMIN, CLIENTE y EMPRESA ahora guardan también la columna tipo_usuario (fija por CHECK) y su FK
    hacia USUARIO es compuesta (numero_identificacion, tipo_usuario). Esto, sumado a un trigger de restricción diferido
    (CONSTRAINT TRIGGER) sobre USUARIO, garantiza que la herencia sea disjunta (ya lo era) y TOTAL (antes no se exigía: un
    USUARIO podía quedar sin fila de subtipo). Ver sección TRIGGERS en el schema.sql.
  - VERIFICACION: se agrega un índice único parcial (numero_identificacion, tipo) WHERE estado = 'Pendiente'. Antes nada impedía
    que un mismo usuario tuviera varias verificaciones del mismo tipo abiertas a la vez; ahora solo se permite una pendiente por
    tipo, sin bloquear reintentos después de que la anterior se resuelve (Aprobada/Rechazada).
  - EVENTO.id_creador: se agrega un trigger que valida que el creador tenga tipo_usuario CLIENTE o EMPRESA (antes la regla
    "ADMIN no crea eventos" solo estaba en texto, sin mecanismo que la hiciera cumplir).
  - Se agrega la sección ÍNDICES RECOMENDADOS con los índices de búsqueda que necesitan los reportes del backlog (ingresos,
    cobertura geográfica, cancelaciones) y que antes solo estaban implícitos en el índice espacial de UBICACION.
  - Se documenta explícitamente por qué el "borrado lógico" no es uniforme: USUARIO usa estado_cuenta (ENUM con significado de
    ciclo de vida de la cuenta: Activa/Inactiva), mientras que los catálogos (CATEGORIA, PROVEEDOR_PAGO) usan activo BOOLEAN
    (simple interruptor de visibilidad). Es una decisión consciente, no una inconsistencia.
  - Las reglas de negocio (cupos, edad mínima, verificación biométrica aprobada, etc.) se implementan como triggers en la base
    de datos (no en el backend) para que la integridad no dependa de qué capa de la aplicación inserte los datos. El DDL
    completo con estos triggers está en database/schema.sql.

----------------------------------------------------------------------------------------------------------------------------------
CRITERIO PARA ESCOGER EL TIPO DE CADA CAMPO
----------------------------------------------------------------------------------------------------------------------------------
  ENUM                  Opciones fijas que define el sistema y casi nunca cambian (estados, roles, jornada). Agregar un valor
                        exige ALTER TYPE.
  Tabla catálogo + FK   Opciones largas, que pueden crecer o que necesitan datos extra (departamento, ciudad, categoría, proveedor
                        de pago, causas de cancelación). Agregar una es un INSERT.
  VARCHAR / TEXT        Solo para lo que de verdad se escribe libre (nombres, correo, dirección, descripciones) o lo genera el
                        sistema (hash, token, rutas de archivo). Lleva longitud máxima y CHECK de formato cuando aplica.
  En los catálogos      El campo nombre es VARCHAR, pero lo carga un script una sola vez; el usuario solo escoge de la lista, así
                        que no puede escribirlo mal.

----------------------------------------------------------------------------------------------------------------------------------
CONVENCIONES
----------------------------------------------------------------------------------------------------------------------------------
  PK / FK / UQ     Clave primaria / Clave foránea (→ tabla.campo) / Valor único. UQ* = único compuesto (ver reglas).
  Nulo NO / SÍ     NO = obligatorio (NOT NULL). SÍ = opcional.
  Tipo *_t         Tipo ENUM propio (CREATE TYPE ... AS ENUM). Sus valores están en la sección TIPOS ENUMERADOS.
  DERIVADO         Se calcula en consulta; no se almacena.
  Moneda / fechas  Pesos colombianos (COP). TIMESTAMP en hora de Colombia (America/Bogota).

  Columna 'Entrada' (cómo llega el dato; solo 'Texto' se digita libremente):
    Lista          Desplegable con opciones fijas (ENUM) o con registros de otra tabla (FK).
    Lista dep.     Desplegable filtrado por la opción anterior (departamento → ciudad).
    Lista múlt.    Casillas de selección múltiple.
    Catálogo       Dato precargado por script/administrador; el usuario solo lo escoge.
    Lógico         Casilla Sí/No (BOOLEAN).
    Número / Fecha Campo numérico / selector de fecha y hora.
    Mapa           Se obtiene al marcar un punto en el mapa.
    Archivo        Se sube una imagen; se guarda la ruta.
    Texto          Escritura libre, con longitud máxima y validación de formato cuando aplica.
    Sistema / Auto Lo asigna el backend o la BD (sesión, fecha actual, SERIAL, pasarela); el usuario no lo escribe.

Clave primaria: (id_pais)

Campo                    Tipo                   Nulo Clave   Default            Entrada     Descripción
------------------------ ---------------------- ---- ------- ------------------ ----------- --------------------------------------
id_pais                  SERIAL                 NO   PK      auto               Auto        Identificador único del país.
nombre                   VARCHAR(60)            NO   UQ                         Catálogo    Nombre del país. Carga inicial:
                                                                                            Colombia.

Restricciones y reglas:
  - El usuario no escoge el país: el formulario arranca directamente en la lista de departamentos de Colombia.

Relaciones:
  - PAIS 1:N DEPARTAMENTO.

2. TABLA: DEPARTAMENTO
==================================================================================================================================
Descripción: Catálogo de los departamentos de Colombia (lista precargada desde la DIVIPOLA del DANE).
Clave primaria: (id_departamento)

Campo                    Tipo                   Nulo Clave   Default            Entrada     Descripción
------------------------ ---------------------- ---- ------- ------------------ ----------- --------------------------------------
id_departamento          SERIAL                 NO   PK      auto               Auto        Identificador único del departamento.
codigo_dane              CHAR(2)                NO   UQ                         Catálogo    CAMBIO: código DANE del departamento

nombre                   VARCHAR(60)            NO                              Catálogo    Nombre oficial (ej. Valle del Cauca).

Relaciones:
  - DEPARTAMENTO N:1 PAIS.
  - DEPARTAMENTO 1:N CIUDAD.

==================================================================================================================================

4. TABLA: UBICACION
==================================================================================================================================
Descripción: Dirección y punto en el mapa (PostGIS). Cada ubicación tiene un solo dueño: un USUARIO o un LUGAR.
Clave primaria: (id_ubicacion)

Campo                    Tipo                   Nulo Clave   Default            Entrada     Descripción
------------------------ ---------------------- ---- ------- ------------------ ----------- --------------------------------------
id_ubicacion             SERIAL                 NO   PK      auto               Auto        Identificador único de la ubicación.
direccion                VARCHAR(150)           NO                              Texto/Mapa  Dirección física; se autocompleta al
                                                                                            marcar el punto en el mapa y se puede
                                                                                            ajustar.
coordenadas              GEOGRAPHY(Point,4326)  NO                              Mapa        CAMBIO: reemplaza latitud y longitud.
                                                                                            Punto marcado en el mapa (no se
                                                                                            digita).
id_ciudad                INTEGER                NO   FK                         Lista dep.  Ciudad escogida en la cascada
                                                                                            departamento → ciudad. →
                                                                                            CIUDAD.id_ciudad

Restricciones y reglas:
  - Índice espacial: CREATE INDEX idx_ubicacion_coord ON UBICACION USING GIST (coordenadas);
  - Latitud y longitud se leen con ST_Y(coordenadas::geometry) y ST_X(coordenadas::geometry); por eso ya no se guardan aparte.
  - Eventos a menos de 5 km del usuario: ST_DWithin(lugar.coordenadas, usuario.coordenadas, 5000).
  - El punto debe estar dentro de Colombia: CHECK ST_Y(coordenadas::geometry) BETWEEN -4.3 AND 13.6 AND
    ST_X(coordenadas::geometry) BETWEEN -82.0 AND -66.8.
  - Solo se guarda id_ciudad; el país y la división se obtienen por la cadena de FK (guardarlos rompería la 3FN).

Relaciones:
  - UBICACION N:1 CIUDAD.
  - USUARIO 1:1 UBICACION (UbiPer).
  - LUGAR 1:1 UBICACION (UbiLug).

             el número de identificación.
Clave primaria: (numero_identificacion)

Campo                    Tipo                   Nulo Clave   Default            Entrada     Descripción
------------------------ ---------------------- ---- ------- ------------------ ----------- --------------------------------------

                                                                                            guiones ni espacios.

tipo_usuario             tipo_usuario_t         NO   UQ*                        Lista       Rol de la cuenta.
correo                   VARCHAR(100)           NO   UQ                         Texto       Correo electrónico; se usa para
                                                                                            iniciar sesión.

  - Las FK hacia USUARIO usan ON UPDATE CASCADE por si se corrige un número de documento.
  - Eliminar un usuario = estado_cuenta 'Inactiva'; no se borra físicamente si tiene tickets o pagos.

Relaciones:
  - USUARIO 1:1 UBICACION.
  - USUARIO 1:N TELEFONO_USUARIO.
  - USUARIO 1:N VERIFICACION (Comprueba).
  - Subtipos: ADMIN, CLIENTE, EMPRESA.

##################################################################################################################################
# REGLAS DE NEGOCIO GENERALES (triggers / CHECK)
##################################################################################################################################
  - Un cliente solo puede tener un ticket por evento (los Cancelados no cuentan); para inscribirse debe tener verificación
    biométrica Aprobada.
  - Edad del cliente >= edad_minima del evento.
  - Tickets <= cupo del nivel; suma de cupos <= capacidad_total; capacidad_total <= capacidad_maxima del LUGAR.
  - Si quien crea el evento es CLIENTE, todos los niveles tienen precio 0. ADMIN no crea eventos.
  - Crea (EVENTO.id_creador) es la única relación que usan los reportes de ingresos y de eventos por empresa. Organiza nunca
    entra en cálculos de dinero.
  - Solo reseña quien tiene ticket en estado Usado.
  - SESION_ADMIN se inserta al cerrar sesión (logout o expiración), con ambas horas.
  - Eliminar un usuario = estado_cuenta 'Inactiva'; no se borra físicamente si tiene tickets o pagos.
  - Ingresos netos = pagos aprobados - monto_reembolsado.
  - Una UBICACION pertenece a un solo dueño (USUARIO o LUGAR); nunca se comparte.

  Fuera de alcance (recortado por el equipo): puntos del cliente y visualización de publicidad.
